# Star Compiler — Next Steps
1. Complete Priority Roadmap

## Priority Roadmap (derived from current_status.md suitability analysis)

Ordered biggest win → smallest, where "win" = how much it unblocks writing useful
programs relative to implementation effort.

### 3. Networking basics
Sockets/HTTP client — needed for anything client/server. Natural follow-on once
FFI (#1) exists (bind to existing socket libs) or as direct builtins otherwise.
- Raw TCP socket connect/send/recv as a floor.
- Defer HTTP parsing to a library (via FFI) rather than building it into the compiler.

### 4. Graphics / audio / input bindings
Core to the "game language" pitch but currently 100% aspirational
(`draw_sprite`, `flash_screen`, `wait` are documented but not implemented).
Highest effort of the "unlock capability" items — best sequenced after FFI (#1)
so it's a binding to SDL/similar rather than a from-scratch renderer.
- Window creation + framebuffer/pixel-blit as the minimal viable slice.
- Input polling (keyboard/mouse/gamepad).
- Audio playback (defer to last — least blocking for "useful program" broadly).

### 5. Module system: re-exports, search paths, manifest
Needed once any program grows past a few files. Current system only inlines one
relative-path file at a time with no transitive symbol visibility.
- Transitive re-export so `a` importing `b` importing `c` can reach `c`'s symbols.
- Search-path resolution instead of hand-written relative paths everywhere.
- Minimal package manifest (name, version, entry point) — defer a full package
  manager/registry until there's more than one real multi-file project to learn from.

### 6. Expand core standard library
The current 28 builtins cover almost no string/collection manipulation beyond
`List<T>`. Grow incrementally as real programs (see #8) expose actual gaps
rather than speculatively.
- String ops: split/join/trim/replace/contains/format beyond f-strings.
- A `Map`/`Dict` and `Set` type to complement `List<T>`.
- Fill out math builtins as needed (trig, log/exp, etc.).

### 7. Wire up reflection into an actual runtime feature
`@export`/`@tweakable` currently only emit descriptive metadata strings — there
is no hot-reload runtime or file watcher consuming them yet. Lower priority
since it's a productivity/tooling win, not a capability unlock: nothing is
*impossible* without it, just slower to iterate on.

### 8. Build one real, non-toy program in Star
Everything in `examples/` and `tests/` tops out around ~40 lines of
single-feature demos. FFI and file I/O are now done, which is enough to write
a small file-backed tool; dogfood the language on one program larger than a
toy — this will surface real gaps faster than speculative stdlib growth, and
is the best validation that the "useful programs today" bar has actually
been cleared.

## Last actions:
File I/O builtins:
Language: six new builtins — file_open(path, mode) -> ptr, file_close(handle), file_read(handle) -> str, file_read_line(handle) -> str, file_write(handle, data) -> bool, file_exists(path) -> bool — reusing the extern-FFI ptr type as the file handle rather than adding a new type. Error model: file_open returns a null ptr on failure (checked with the existing is_null()/null_ptr(), exactly like getenv); a null/closed handle passed to file_read/file_read_line/file_write/file_close is treated as a programmer error and aborts loudly (diagnostic + exit(1)), matching the existing frame-overflow/div-by-zero abort philosophy rather than inventing an Option/Result type Star doesn't have; file_read/file_read_line yield an empty str on EOF, matching read_line()'s own EOF convention.

Codegen: new src/codegen/file_io.rs module wrapping fopen/fclose/fread/fwrite/fseek/ftell/fgetc (all core CRT symbols, no extra link flags needed, same as the extern-FFI CRT calls). file_read sizes its buffer up front via ftell/fseek rather than growing incrementally, since the remaining byte count is cheap to compute ahead of a single fread; file_read_line is structurally identical to the existing read_line()'s fixed-buffer char-at-a-time loop, just sourced from fgetc(handle) instead of the stdin-only getchar().

Verified working end-to-end: examples/file_io.star writes a file, checks file_exists on a real and a missing path, then reopens and reads it back with both file_read_line and file_read, producing correct output when run (confirmed against the real file written to disk, not just captured stdout).

Bug-checking round (2026-07-11):

Fixed — method calls on any non-`Ident` receiver produced invalid IR: `Codegen::emit_call_expr`'s method-call path resolved its receiver pointer through a bespoke `receiver_name`+`sym_ptr` combo that only recognized a bare local-variable identifier; every other receiver shape (`self`, a nested field access, a list-index/call-result rvalue) fell through to the literal string `"%undef"`, which only failed at the `clang` step ("use of undefined value '%undef'"). This broke the ordinary OO idiom of one method calling another through `self` (`self.bump()` from inside another method), plus `obj.inner.method()` and `list[i].method()`-style chained calls — nothing in `tests/frontend.rs` exercised any of these. Fixed by routing through the existing `Codegen::emit_place`, which already correctly resolves all of these receiver shapes (including spilling an arbitrary rvalue into a fresh alloca). Regression tests: `runtime_method_call_through_self_end_to_end`, `runtime_method_call_on_nested_field_receiver_end_to_end`, `runtime_method_call_on_list_index_receiver_end_to_end`.

Fixed — builtin calls had no argument count/type validation: unlike ordinary/extern-fn calls (`Checker::check_call_args`), builtin calls (`file_open`, `dot`, `clamp`, `is_null`, ...) are dispatched by name via `builtin_return_ty` and previously had zero argument validation beyond `print`/`println`'s own special case. Several builtin codegen functions (`emit_abs`/`emit_dot`/`emit_clamp`/`emit_lerp`/`emit_file_open`/...) `untag` one argument's register using *another* argument's inferred type, so a caller passing an unexpected type (`file_open(42, 3.5)`, `clamp("x", 1, 5)`, `dot(v2, v3)`) type-checked cleanly and only failed at the `clang` step with a confusing, mislocated error. Added `Checker::check_builtin_call_args`, covering every builtin's real arity/type expectations (permissive where the codegen genuinely is, e.g. `min`/`max`'s per-argument int-or-float promotion). Also converted two existing file-I/O arity tests (`codegen_file_open_reports_missing_argument`/`codegen_file_write_reports_missing_argument`) from "caught only at codegen" to `checker_rejects_*` now that they're caught earlier, and added new tests for the type-mismatch cases this closes.

Fixed — `List<T>` had no memory ownership model (copy-on-write RC, 2026-07-11):

`Ty::List`'s value used to be a plain `{data, len, cap}` struct copied by bit value on every `let`/reassignment (no RC indirection, unlike `Str`), so `let b = a` made `a`/`b` alias the same `malloc`'d buffer; `push`'s grow path freed the old buffer and repointed only the pushed-into variable's fields, leaving the other alias's `data` pointer dangling (a real, confirmed use-after-free). Separately, `contains_rc(List<T>)` only recursed into the *element* type, so a list of non-RC elements (`List<i32>`, ...) was never `track_owned` and its buffer leaked unconditionally.

Decision: after weighing RC-sharing (like `Str`, reference semantics), deep-copy-on-assignment (value semantics, O(n) copies), and copy-on-write against each other, went with **copy-on-write**: `List<T>` now lowers to a reference-counted `i8*` object pointer, the same allocation shape `Str` already uses (`star_rc_alloc`/`retain`/`release`, reused verbatim), pointing at a heap payload `{ T* data, i64 len, i64 cap }`. `let b = a` is an O(1) refcount bump; any *mutation* (`push`, `pop`, index-assignment) goes through a new `Codegen::emit_list_ensure_unique` gate first, which clones the buffer (mallocing a fresh one, `memcpy`ing the live prefix, retaining any RC-bearing elements) whenever the refcount shows more than one owner — so mutating one binding is never observable through another, while non-mutating copies stay free. This matches the ownership semantics the type already documented, without `List<T>` overlapping what `GenRef<T>`'s shared arena is for.

`contains_rc(Ty::List(_))` is now unconditionally `true` (was gated on the element type), fixing the leak for non-RC element types too — a `List<T>`'s own buffer is always released now, via a lazily-generated, per-element-type `list_release_<mangled>` thunk (`Codegen::list_release_thunk_operand`, mirrors the closure `_release_env` thunk pattern) that frees the buffer and, only if the element type carries RC content, loops releasing each element first.

One bug caught only by manually rebuilding and running the example binaries (the pre-existing `runtime_lists_end_to_end` test was silently running a *stale* checked-in `.exe` that predated this change): reading `.len()`/`[i]` on a list that was constructed but never mutated (`List<i32>()`, still `null`) dereferenced through the null object pointer and segfaulted. Fixed by giving the read path (`Codegen::list_fields`) its own null-guarded branch (`data = null, len = 0` via `phi` when the object pointer is null), distinct from the mutating path (`list_fields_mut`), which already gets a guaranteed-non-null object from `emit_list_ensure_unique`.

Regression tests: `runtime_list_cow_push_does_not_corrupt_alias_end_to_end` (the original UAF repro), `runtime_list_cow_index_assignment_diverges_end_to_end`, `runtime_list_cow_pop_diverges_end_to_end`, `runtime_list_cow_clone_retains_str_elements_end_to_end`, `codegen_list_of_int_is_released_at_scope_exit`. Rewrote the codegen-IR-shape tests that asserted on the old inline-struct representation (`codegen_list_new_is_null` (renamed), `codegen_list_of_str_release_uses_runtime_loop`, `codegen_list_of_vec2_uses_native_vector_element`). Rebuilt and manually re-verified all four `List<T>`-using example binaries (`lists.exe`, `rc_strings.exe`, `str_fixes.exe`, `rc_closures.exe`) against the new codegen, not just the test suite.

Fixed — closures capturing `self` by pointer could dangle from any local struct, not just `frame:`-scoped ones (2026-07-11):

`src/types/frame_analysis.rs`'s escape analysis previously only tracked `let`-bindings declared inside a `frame:` block (`frame_locals`); a method returning a closure that captures `self` (always by pointer — `Codegen::captured_value_llvm_ty`) called on an ordinary function-local struct or a by-value parameter had the exact same dangling-pointer problem once that closure escaped the function, but sailed straight past the check since neither kind of local was tracked at all.

Investigated whether any receiver shape *is* safe to exempt (the "arena `GenRef`" concern the bug write-up raised) by reading `Codegen::emit_place`: every receiver shape other than a bare local/`self`/nested field access — including a `GenRef` dereference — is spilled into a *fresh, function-scoped* alloca before its address is handed to the callee, so there is no receiver shape in the current codegen whose pointer outlives the enclosing function. That ruled out a narrower exemption-based fix.

Fix: added a second, broader tracking set (`local_structs`) alongside the existing `frame_locals`, seeded with every by-value `Ty::Named` parameter (`self` itself excluded — its safety is the *caller's* responsibility, independently checked when the caller's own body is analyzed) and every `let`-bound struct local regardless of frame-ness. Deliberately kept `local_structs` separate from `frame_locals` rather than merging them: the existing `Assign`/`Return`/tail/`Spawn` checks for a *plain* (non-closure) struct value stay scoped to `frame_locals` only, since an ordinary struct's value is always a safe, independent copy when returned/assigned — broadening those to ordinary locals would have rejected sound, extremely common code (`let p = Point(1,2); return p`). Only the closure-escaping-through-a-method-call check (the `TypedExpr::Call` arm) consults the broader `local_structs` set.

Regression tests: `rejects_closure_capturing_plain_local_self_escaping_via_return` (the todo.md repro), `rejects_closure_capturing_by_value_param_self_escaping_via_return`, `accepts_closure_capturing_plain_local_self_used_within_same_function` (using the closure without escaping stays legal), `accepts_returning_plain_local_struct_by_value` (guards against the over-rejection risk the write-up flagged).

Minimal OS surface: argv + env vars (2026-07-11):

Three new builtins -- `args() -> List<str>`, `env_get(name: str) -> str`, `env_set(name: str, value: str) -> bool`.

`args()`: the OS/CRT always calls the real, linked `main` with `argc`/`argv` regardless of what Star's own `fn main()` declares (every existing program declares it with no parameters) -- tried reading them via mingw's documented `__argc`/`__argv` CRT globals first (would have needed zero changes to `main`'s own codegen), but confirmed by hand-compiling a standalone `.ll` that this toolchain's linker doesn't export them (`undefined symbol: __argc`/`__argv`). Went with the other standard approach instead: `Codegen::emit_fn`'s `is_main` special case now always emits `i32 @main(i32 %.argc, i8** %.argv)` (overriding Star `fn main()`'s own, always-empty declared parameter list) and stores both into new globals `@star.argc`/`@star.argv` in `main`'s entry block, confirmed working the same way. `emit_args` (`src/codegen/list.rs`, alongside the rest of `List<T>`'s construction logic since it needs the same private payload/release-thunk helpers `emit_list_lit` uses) then builds an ordinary `List<str>` from them at call time, duplicating each `argv[i]` into a fresh owned `str` (argv's C strings have no RC header) the same way `emit_ptr_to_str` bridges any other foreign `char*`. Includes `argv[0]` (the program path), matching the OS/CRT's own argv convention. This only changes `main`'s own generated IR -- every other function's codegen, and every existing example's compiled behavior, is unaffected (confirmed: the full pre-existing test suite, including every `Command::new("examples/*.exe")` test that runs a *pre-built, checked-in* binary rather than recompiling, still passes unmodified).

`env_get`/`env_set` (`src/codegen/os.rs`, new module): thin wrappers over `getenv`/`_putenv` (both hand-verified linkable via a standalone `.ll` first, alongside the `__argc`/`__argv` experiment above). `env_get` copies `getenv`'s result into a fresh owned `str` (same bridging reasoning as `args()`), yielding `""` for an unset variable rather than a null `ptr` -- extends `file_read`/`read_line`'s established "empty value on nothing to read" EOF convention to "variable absent" rather than introducing an Option/Result type Star doesn't have. `env_set` builds a transient `"NAME=VALUE"` buffer (plain `malloc`, freed right after the call -- not `star_rc_alloc`'d, since nothing keeps a reference to it once `_putenv` returns, per its documented copy-into-the-process-environment-block behavior) and returns whether the call reported success.

Since `getenv`/`_putenv` are now unconditionally `declare`d by `Codegen::emit_builtins` (same as every other CRT symbol a builtin might need), both were added to `RESERVED_RUNTIME_SYMBOLS` -- an `extern "C" fn getenv` would otherwise collide with the compiler's own `declare`. This broke `examples/extern_ffi.star`'s pre-existing FFI demo (it used `extern "C" fn getenv` to show a `str -> ptr` foreign call) and two tests in `tests/frontend.rs` that also declared `getenv` directly; all three were switched to `strstr` (haystack/needle `str` args, `ptr` return -- same demonstration shape, and incidentally drops a test dependency on the host's `PATH` env var being meaningfully set).

Bug-checking round #2 (2026-07-11): five independently-confirmed bugs, found by parallel Explore-agent surveys of the checker/codegen followed by hand-written `.star` repros compiled and run against a real build before touching any code.

Fixed -- same-named methods on different structs collided in a single flat, name-keyed table (both the checker and codegen): `Checker::check`'s registration pass inserted every impl method into `self.functions` keyed by bare method name only (`self.functions.insert(m.sig.name.clone(), ...)`), so `impl A: fn area(self) -> i32` followed by `impl B: fn area(self, scale: i32) -> i32` meant the second declaration silently overwrote the first's signature project-wide -- `a.area()` type-checked (or failed to) against whichever impl happened to be registered last, confirmed with a repro that produced a bogus "expects 1 argument(s), found 0" on perfectly valid code. Worse, `Codegen::emit_fn` emitted every impl method's LLVM function under its bare name too (`define i32 @area(...)`), so even when both methods' signatures happened to agree, two structs sharing a method name produced two colliding `define @area` globals -- confirmed failing at the `clang` step with "invalid redefinition of function 'area'". Fixed by keying methods per-struct end to end: new `Checker::methods`/`Codegen::methods` maps (both `"{struct}#{method}"` -> signature/mangled-name), and `Codegen::emit_fn` gained an `owner: Option<&str>` parameter so an impl method's emitted LLVM function is mangled `{struct}__{method}` instead of the bare name. Regression tests: `checks_same_named_methods_on_different_structs_with_different_arity`, `runtime_same_named_methods_on_different_structs_dispatch_correctly_end_to_end`, `codegen_impl_method_llvm_name_is_mangled_by_struct` (plus two pre-existing tests -- `codegen_sequence_uses_state_machine`, `codegen_method_self_param_is_not_released_at_scope_exit` -- updated for the new mangled names their asserted IR text depended on).

Fixed -- `Codegen::emit_place` had no arm for `ListIndex`/`GenRefIndex`, so any mutation whose *receiver* was itself an index expression silently discarded the write: `emit_place`'s generic fallback evaluates the expression, spills the resulting *value* into a fresh, disconnected alloca, and returns that throwaway pointer -- correct for a plain read, but any subsequent write through it (a chained `List<T>` method call, a nested index-assignment, a struct-field write) vanished. Confirmed three shapes all silently no-op'd: `outer[0].push(99)` on a `List<List<i32>>` (`outer[0].len()` unchanged afterward), `m[0][1] = 999` on a `List<List<i32>>` (read back unchanged), and `r[0].hp -= 10` through a `GenRef` (arena slot unchanged). Fixed with two new place-resolving helpers mirroring each other: `Codegen::emit_list_index_place` (`list.rs`) reuses `list_fields_mut`'s copy-on-write-ensure-unique gate and returns a real GEP'd pointer into the buffer, with an out-of-bounds index yielding a pointer to a fresh zeroed alloca (matching `store_list_index`'s existing silent-no-op-on-OOB convention); `Codegen::emit_genref_index_place` (`arena.rs`) is the same fix for the identical root cause against an arena slot, with the same zeroed-alloca fallback on a stale generation/OOB index. `emit_place` now routes both expression shapes to these instead of the generic fallback. Regression tests: `runtime_nested_list_index_receiver_push_mutates_through_index_end_to_end`, `runtime_nested_list_index_assignment_end_to_end`, `runtime_genref_field_write_mutates_arena_slot_end_to_end`.

Fixed -- `par`/`swarm` iterated despawned arena slots as if they were live, a real use-after-free for RC-bearing element types: `@arena.{name}.count` is a high-water mark of ever-allocated slots (`despawn` never decrements it, only bumps the slot's generation and pushes it onto the free-list -- see `emit_despawn_stmt`), but `emit_par_stmt`'s generated worker walked `[start, end)` over that raw index range with no liveness check at all. Since `despawn` already releases an RC-bearing slot's content (`emit_release_at`) before marking it dead, a subsequent `par` visiting that slot read/retained an already-released pointer. Confirmed with a repro: `spawn`ing three entities, `despawn`ing the middle one, then a `par` loop printing each -- the despawned entity was visited exactly like a live one. Fixed by adding a generation-parity check (mirroring `emit_genref_index`'s identical liveness check) at the top of each loop iteration in the generated worker, branching around the loop body for any even-generation (dead/never-spawned) slot. Regression tests: `codegen_par_worker_skips_despawned_slots` (IR-shape check for the generated parity branch), `runtime_par_skips_despawned_slot_end_to_end` (end-to-end against a `str` field, so an unfixed version would crash or corrupt the heap rather than just misbehave).

Fixed (caught by writing the test above, a second and independent bug from the same investigation) -- `emit_par_stmt` swapped out `self.ir`/`self.symbols` for the generated worker function's own empty versions but never did the same for `self.owned_stack` (the release-at-scope-exit bookkeeping stack, see `rc.rs`), and never wrapped the loop body in its own `push_scope`/`pop_scope` at all. An RC-owned local declared inside a `par`/`swarm` body (`let t: str = e.name`) called `track_owned`, which pushed onto whichever scope frame happened to be open in the *caller* at the time -- so once codegen returned to the caller and that frame was eventually popped, it tried to release a register that was only ever defined in the worker's own, separate IR buffer, producing invalid LLVM IR ("use of undefined value") at the `clang` step. Fixed by saving/restoring `self.owned_stack` around the worker-function emission (same pattern as the other per-function state) and wrapping the loop body in its own `push_scope()`/`pop_scope(true)`, so an RC-owned per-iteration local is now correctly released once per iteration inside the worker itself. Covered by the same `runtime_par_skips_despawned_slot_end_to_end` test above (its `let t: str = e.name` line is what surfaced this).

Fixed -- unbounded recursion in generic monomorphization crashed the whole compiler process with a Rust stack overflow (no diagnostic at all) on a small, ordinary-looking generic struct: `Checker::instantiate_struct`/`instantiate_enum`/`instantiate_fn` each memoize by mangled name (`Node__Box__i32`) to stop a *literal* self-referential generic, but a field/call that wraps its own type parameter in another generic every step (`struct Node<T>: next: Node<Box<T>>`) produces a *new* mangled name at every recursive step, so the memo check never fires -- confirmed with a four-line repro (`Box<T>`/`Node<T>: next: Node<Box<T>>`/`Root: n: Node<i32>`) that reliably crashed `star.exe check` with "thread 'main' has overflowed its stack" (exit code matching Windows' STATUS_STACK_OVERFLOW). Fixed by adding `Checker::mono_depth`, a counter incremented for the duration of each `instantiate_struct`/`instantiate_enum`/`instantiate_fn` call (each split into a thin depth-tracking wrapper plus an `_inner` function holding the original body unchanged), capped at `MAX_MONO_DEPTH = 64` with a clean diagnostic instead of recursing further -- high enough that no real, finite nested-generic usage should ever hit it. Regression tests: `rejects_infinitely_nested_generic_struct_field_does_not_overflow_stack` (the repro, now a clean checker error instead of a crash), `runtime_finitely_nested_generic_struct_end_to_end` (guards against the depth guard being so aggressive it rejects sound, ordinary nested-generic code like `Box(Box(Box(5)))`).

Other gaps surveyed but *not* fixed this round (lower confidence, larger scope, or design questions better raised with the user first): no match exhaustiveness checking (a non-exhaustive `match` over an enum compiles and falls through to an `undef` value at runtime rather than a checker error -- `src/codegen/expr.rs`'s own comment already flags this as an assumption); generic function calls don't re-validate a repeated type parameter's consistency across arguments (`pair(5, "hello")` against `fn pair<T>(a: T, b: T)` isn't caught); `impl Trait for Type` never checks the impl actually provides every method the trait declares; comparing two `GenRef` values (or a `GenRef` against an unrelated type) with `==` type-checks and only fails with an unlocated error at codegen. All four are checker-side gaps, not memory-safety bugs, and would be reasonable candidates for a future round.

Full regression suite (420 tests, up from 410) passes after all five fixes; every checked-in `examples/*.exe`/`.ll` was rebuilt against the fixed compiler and re-verified (`geometry_lib.star` excepted -- it has no `fn main`, a library file only ever compiled via `import`, unrelated to this round).

Regression tests: checker coverage for all three builtins' return types and arg-count/type validation (`checks_os_surface_builtin_return_types`, `checker_rejects_args_with_arguments`, `checker_rejects_env_get_wrong_arg_count`, `checker_rejects_env_get_non_str_arg`, `checker_rejects_env_set_wrong_arg_count`, `checker_rejects_env_set_non_str_args`, `extern_fn_rejects_getenv_as_reserved_name`), a codegen-shape test for `main`'s forced `argc`/`argv` signature (`codegen_main_accepts_argc_argv_params`), and end-to-end runtime tests covering `args()` with/without extra argv entries (`runtime_args_includes_program_path_and_extra_args_end_to_end`, `runtime_args_has_only_program_path_when_no_extra_args_end_to_end`), `env_get` against both a missing and a preset-in-the-real-environment variable (`runtime_env_get_missing_var_returns_empty_string_end_to_end`, `runtime_env_get_reads_preset_environment_variable_end_to_end`), and `env_set` round-tripping and overwriting an existing value (`runtime_env_set_round_trip_end_to_end`, `runtime_env_set_overwrites_existing_value_end_to_end`). New example `examples/os_surface.star` (built/verified against a real run with extra argv entries) exercises all three builtins together end to end.

Bug-checking round #3 (2026-07-12): eight independently-confirmed bugs, found by five parallel Explore-agent surveys (lexer/parser, type checker, control-flow codegen, memory-model codegen, and the smaller/newer subsystems -- the memory-model agent's run failed partway through on an unrelated session-limit error and wasn't re-spawned, so that area got comparatively less coverage this round) followed by hand-written `.star`/raw-`.ll` repros compiled and run against a real build, plus one further bug (the most severe of the round) found by manually rebuilding and exit-code-checking every checked-in example afterward.

Fixed -- an f-string used as an ordinary value (anything other than the direct, sole argument to `print`/`println`) segfaulted: `Codegen::emit_expr`'s generic `TypedExpr::FStr` arm built the `%d`/`%f`/`%s` format string and evaluated each interpolated hole's expression, but never actually substituted them -- it returned the bare, unformatted template-string pointer as the f-string's *value*. `let s = f"x is {x}!"` stored literal `%d` bytes in `s`; printing `s` later fed `printf` a format string with unsupplied varargs. This only affected the non-print-argument path -- `println(f"...")`/`print(f"...")` directly already had their own correct, separate codegen (`emit_print_like`). Fixed by materializing a real, fully-substituted, owned `str` via two `snprintf` calls (first sized `null`/`0` to get the required length, matching the length-then-fill idiom `emit_str_concat`/`emit_ptr_to_str` already use for `star_rc_alloc`-backed buffers, then filled) rather than streaming to `printf`; no trailing newline is added (that's `print`/`println`'s own convention, not a generic value's). Regression tests: `runtime_fstring_bound_to_let_then_printed_end_to_end`, `runtime_fstring_returned_from_function_end_to_end`, `runtime_fstring_value_all_hole_types_end_to_end`, `runtime_fstring_value_borrowing_str_read_does_not_corrupt_original_end_to_end`, `runtime_fstring_value_nested_and_concat_end_to_end`.

Fixed -- undefined identifiers, undefined functions, and `self` outside any method all silently type-checked: `Checker::infer_expr`'s `Expr::Ident` arm fell back to the `unknown` placeholder type for any name found in neither `vars` nor `self.functions`, with no diagnostic at all (and `Expr::SelfExpr` similarly fell back to a placeholder `Self` type when no `self` param was in scope) -- a typo'd variable/function name, or `self` used in a bare top-level `fn`, type-checked cleanly and only broke at the `clang` step against generated IR referencing `%unknown`/an unresolvable `Self`. Fixed by checking `self.functions`/`self.generic_fns`/`is_builtin_name` before falling back, and reporting "undefined name" (with a `did you mean` suggestion off `vars`/`self.functions`) otherwise; `self` outside a method is now its own clean error. Regression tests: `rejects_undefined_identifier`, `rejects_undefined_identifier_in_fstring_interpolation`, `rejects_self_outside_method`, `accepts_call_to_declared_function`.

Fixed -- a struct/enum pattern matched against a scrutinee of the *wrong shape entirely* (not just the wrong same-shape type) skipped the mismatch check: `check_match_arm` only reported "pattern does not match scrutinee type" inside `if let Ty::Named(..) = scrutinee_ty` (struct patterns) / `if let Ty::Enum(..) = ...` (enum patterns) -- scrutinees of any *other* type (`i32`, `bool`, `List<T>`, a vector, ...) simply didn't match that `if let`, so the check silently no-op'd and the arm proceeded to GEP into a struct/tagged-union layout the scrutinee never had, failing only at the `clang` step. Fixed by adding the `else` arm the missing shape needed. Regression tests: `rejects_struct_pattern_against_non_named_scrutinee`, `rejects_enum_pattern_against_non_enum_scrutinee`.

Fixed -- a bare, un-negated integer literal of exactly `i32::MAX + 1` (`2147483648`) silently became `i32::MIN` (`-2147483648`) with zero diagnostics: the lexer's special case for spelling `i32::MIN` as `-2147483648` (magnitude `2147483648` plus a separate, preceding unary `-` token) converted the *bare* magnitude to `i32::MIN`'s bit pattern unconditionally, regardless of whether a unary minus actually preceded it -- since normal digit scanning never otherwise produces a negative token value, any `Expr::Int` reaching the checker with a negative value is *always* this ambiguous case. Fixed at the checker level rather than the lexer/parser (no context there to disambiguate cleanly): `Checker::infer_expr`'s `Expr::Unary`/`Neg` arm now intercepts the exact sanctioned shape (`-` directly over this one literal magnitude) before generically recursing, collapsing it straight to the `i32::MIN` literal; the generic `Expr::Int` arm reports the same "too large" error the lexer already gives other out-of-range literals for any *other* (un-negated) occurrence of that value. Regression tests: `rejects_bare_i32_max_plus_one_literal` (`accepts_i32_min_literal` already covered the legal `-2147483648` spelling and continues to pass unchanged).

Fixed (most severe of this round: a heap buffer overflow, found via manual code audit of `Codegen::type_size`'s call sites, then confirmed with an empirically-derived LLVM struct-layout probe and a real pre/post-fix repro) -- `Codegen::type_size` computed a struct's byte size by naively summing each field's size with **no alignment padding at all**, silently *undersizing* any struct mixing a sub-8-byte field (`bool`/`i32`/`float`) with an 8-or-16-byte-aligned one (`str`/`List<T>`/a named struct/`ptr`/a vector type). This function backs four call sites that allocate a buffer sized in Rust and then index/stride through it via LLVM's own `getelementptr` (which uses the *real*, padded struct size) -- a real mismatch, not just cosmetic: `arena`'s `spawn` (`malloc`'d backing buffer undersized relative to `GenRef`'s GEP-computed stride -- confirmed as an actual segfault, spawning 700 `{bool, str}` elements into a 1024-capacity arena), `List<T>` literal construction, `List<T>`'s copy-on-write clone (undersized *and* under-`memcpy`'d, silently truncating carried-over elements), `List<T>.push`'s grow path (same double fault), and the `frame:` bump allocator (an undersized per-`let` slot silently corrupts whatever the *next* frame-allocated value occupies, without ever tripping the total-capacity overflow guard). Fixed two ways: (1) `type_size`'s `Ty::Named` case now properly models real LLVM struct layout (per-field alignment padding + trailing pad to the struct's own widest-field alignment), backed by a new `Codegen::type_align` (LLVM ABI alignment per type, empirically confirmed via a standalone `.ll` probe rather than assumed -- notably `<3 x float>`/`<4 x float>` both occupy 16 bytes of struct-layout space and align to 16 on this target, not the naively-expected 12/16 at align 4) -- this alone fixes `emit_reflect_metadata`'s field-offset string, which has no choice but to model layout in Rust since it bakes offsets into a compile-time constant. (2) The four memory-safety-critical allocation sites no longer trust *any* Rust-side size model at all -- they now ask LLVM itself for a type's real size at codegen time via a new `Codegen::emit_sizeof_llvm_ty` (the standard `getelementptr`-on-`null`-pointer-plus-`ptrtoint` idiom), which is correct by construction regardless of nesting/vector shape. Regression tests: `codegen_reflect_metadata_offsets_account_for_field_alignment`, `runtime_arena_of_padded_struct_spawns_past_naive_size_boundary_end_to_end` (reproduced as a real segfault against the pre-fix compiler, confirmed fixed against the post-fix one), `runtime_list_of_padded_struct_push_past_growth_end_to_end`; existing `codegen_list_literal_allocates_and_stores` updated for the new IR shape (a computed `getelementptr`+`ptrtoint` size rather than a baked-in constant).

Fixed -- a `sequence` local or parameter named `state` silently collided with the desugared struct's own hidden resume-dispatch counter field (`Sequence::desugar_sequence` unconditionally appends a trailing `state: i32` field, but never checked for a same-named user param/local): the coroutine's own "advance to next segment" write and the user's own reads/writes of their `state` variable shared one struct field with no diagnostic, silently corrupting control flow. Fixed by rejecting the collision at desugar time for both a hoisted local and a parameter named `state`. Regression tests: `rejects_sequence_local_named_state`, `rejects_sequence_param_named_state`.

Fixed -- unbounded recursion in the parser overflowed the real Rust call stack with a bare, undiagnosed process abort: `Parser::parse_unary`/`parse_postfix`/`parse_primary`'s mutual recursion (parenthesized groups, unary chains, nested calls/brackets) had no depth limit, so ~500 levels of nested parens or a long unary-minus chain crashed with no diagnostic at all -- the parser-side counterpart of the same class of bug `Checker::mono_depth` already guards against for generic monomorphization. Fixed with the identical pattern: a new `Parser::expr_depth` counter, incremented/checked in a thin wrapper around `parse_unary` (the one shared entry point both nested-parens and unary-chain recursion pass through), capped at `MAX_EXPR_DEPTH = 200` with a clean diagnostic. Regression tests: `rejects_deeply_nested_parens_does_not_overflow_stack`, `rejects_deeply_nested_unary_minus_does_not_overflow_stack`, `runtime_moderately_nested_parens_end_to_end` (guards against the depth guard being so aggressive it rejects sound, if unusual, code).

Fixed (found only by manually rebuilding every checked-in example against the fixed compiler and checking real Windows exit codes -- via PowerShell's `$LASTEXITCODE`, since neither bash's nor the Rust test harness's own exit-status reporting reliably surfaces this particular failure the same way) -- calling a closure that captured another RC-bearing value (a `str`, or -- the actually-hit case -- another closure) corrupted the heap, surfacing as a real `STATUS_HEAP_CORRUPTION` (`0xC0000374`) crash once enough closures were released: `Codegen::emit_closure_lit`'s body-reconstruction loop `track_owned`'d every captured variable except `self`, so `pop_scope` released each captured RC-bearing value at the end of *every call* to the closure -- but the environment holds exactly *one* retained reference per RC-bearing capture (taken once at construction, meant to be released exactly once, via the generated `..._release_env` thunk, when the environment's own refcount reaches zero). Calling a closure that captured an RC-bearing value even once over-released it by one, so it hit zero and was freed while its original binding (or another closure that also captured it) still held a live reference, corrupting the heap once that other owner was released in turn. Notably, this never corrupted *stdout* -- every example's printed output was already completely correct -- only the process's exit status, which is exactly why `examples/closures.exe` (built and run correctly for who knows how many prior rounds) had gone unnoticed: nothing in the existing test suite or manual verification had checked its real exit code against this specific crash class before. Fixed by never `track_owned`-ing a captured variable at all (matching how `self` was already excluded) -- every captured value is a *borrowed* view into the environment's single owned reference for the duration of one call, not a fresh owner. Regression tests: `runtime_closure_capturing_another_closure_called_once_does_not_corrupt_heap_end_to_end`, `runtime_multiple_closures_capturing_each_other_called_then_released_end_to_end` (the exact `examples/closures.star` shape that first surfaced this).

Full regression suite (442 tests, up from 420) passes after all eight fixes; every checked-in `examples/*.exe`/`.ll` was rebuilt against the fixed compiler and re-run with its real exit code checked via PowerShell (not just stdout content, per the closure bug above) -- all pass or (for the two intentional-abort demos, `frame_overflow`/`int_div_by_zero`) exit exactly `1` as designed (`geometry_lib.star` excepted, as before -- no `fn main`).

Other gaps surveyed but *not* fixed this round: an f-string interpolation hole containing a nested string literal with a `}` inside it (`f"{"}"}"`) confuses the lexer's brace-matching (no awareness of quotes) into an "unterminated string" error -- narrow, since there's no other way to produce a literal `{`/`}` in Star source, low priority. Reusing the same `import` alias for two different files that both define a same-named top-level item surfaces as a raw `clang` "invalid redefinition" error rather than a Star diagnostic (`Sequence`/`resolve_inner`/`rename_module` never validates alias uniqueness) -- a diagnostics-quality gap, not a crash. Both, plus the four checker-side gaps already on record from the previous round (non-exhaustive `match` falling through to `undef`, generic type-parameter consistency, `impl Trait` completeness, `GenRef` `==` comparisons), remain reasonable candidates for a future round. The memory-model area (closures/arena/rc/list internals beyond what got covered by chasing the heap-corruption bug above, `GenRef`, frame-allocator/recursion interaction) also warrants a dedicated re-survey, since this round's agent covering it didn't complete.
