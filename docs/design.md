The Star programming language architecture is expressly built to resolve the tension between developer velocity and high-performance game execution. The syntax strips away the noise of semicolons and curly braces in favor of clean, Python-inspired indentation, while retaining the robust type inference, pattern matching, and immutability-by-default of Rust. Furthermore, it avoids rigid OOP inheritance in favor of a hybrid approach combining data objects with behavior implementations.

# Memory
1. Temporal Allocations (frame Context)
Objective: Managing ephemeral data, transient calculations (like A* pathfinding nodes), and intermediate states.

The Mechanism: The frame keyword introduces an implicit bump allocator that resets its pointer to zero at the end of each tick.

Performance Benefits: This grants massive cache locality and ensures allocations and deallocations are highly performant $O(1)$ operations with zero fragmentation.

Compiler Requirements & Safety: The primary danger of frame allocation is pointer escape, where a long-lived object attempts to read overwritten frame memory, causing non-deterministic bugs. To guarantee safety without a GC, the compiler enforces a strict escape analysis (akin to a specialized borrow checker). This guarantees that frame pointers can never be assigned to lifetimes exceeding the current tick.

2. First-Class Spatial Arenas
Objective: Managing macro-level state, large domain groupings, and level-loading lifecycles.

The Mechanism: Spatial arenas are first-class language citizens and serve as the default allocation space for long-lived objects.

Performance Benefits: Entire arenas (e.g., a "Forest Level") can be dropped in a single CPU instruction for $O(1)$ mass deallocation, perfectly aligning with how game states are loaded and unloaded.

Architectural Refinements: While arenas solve traditional memory leaks (forgetting to free a specific object), developers must still manage "logical leaks". For example, infinitely spawning entities into a persistent arena will eventually trigger an Out-of-Memory (OOM) crash. To support dynamic creation and destruction during a level's lifespan, the spatial arenas implement an internal free-list to manage fragmentation.

3. Generational References
Objective: Managing the heavily interconnected "Game Graph" and cross-arena communications where strict borrow checking fails due to unpredictable object mutations and lifetimes.

The Mechanism: Objects are referenced using a Generational ID (a slot-map pattern) rather than direct memory pointers. This ID pairs an index with a generation counter.

Safety and Efficacy: If an entity is destroyed and its memory reused, the generation increments. This cleanly solves the ABA problem (where reassigned memory is mistaken for the original object) and bypasses the overhead of Atomic Reference Counting (ARC).

Validation Check: When dereferencing an ID, the software automatically validates that the array's generation matches the ID's generation. While this requires a minor CPU branch-check overhead, it safely prevents segfaults and returns a safe null/None equivalent if the target is gone. Hardware-level validation is only utilized if compiled for specific architectures supporting memory tagging (like ARM MTE).

Architectural Synergy
By intersecting these three paradigms, it provides a highly cohesive, deeply hacking-friendly philosophy for engine development:
Arenas handle the macro (The World).
Frame handles the micro (The Math).
Generational IDs handle the relationships (The Logic).

This triad completely circumvents the need for a standard Garbage Collector, offering engine developers fine-grained, deterministic control over their memory without exposing them to the catastrophic dangers of manual malloc and free.


# Syntax
1. The Syntax: Pythonic Rust
To eliminate syntactic noise, we strip away the semicolons and curly braces, relying on clean indentation. However, we keep Rust's powerful type inference and immutability-by-default to ensure the code remains robust.

Instead of heavy OOP inheritance (which often leads to rigid, fragile base-class problems in game design), we can use a hybrid approach: Data objects + Behavior implementations, similar to Rust, but with less boilerplate.

```Python
# 'mut' is required to change state. Types are inferred but can be explicit.
struct Vec3:
    x: f32 = 0.0
    y: f32 = 0.0
    z: f32 = 0.0

struct Player:
    mut health: i32 = 100
    position: Vec3 = Vec3(0, 0, 0)
    name: String

trait Damageable:
    fn take_damage(mut self, amount: i32)

impl Damageable for Player:
    fn take_damage(mut self, amount: i32):
        self.health -= amount
        match self.health:
            <= 0 -> print(f"{self.name} has perished.")
            _    -> print(f"Health critical: {self.health}")

fn main():
    let p = Player(health = 100, position = Vec3(0, 0, 0), name = "Hero")
    p.take_damage(150)

```
Notice the match statement—Rust's pattern matching is too good to leave behind, but we can make it visually lighter.

2. Trait Dispatch: Decision and Scope
The `Damageable` example above only ever needs one concrete type (`Player`) at its one call site, and that's not an accident of a small example -- it's the whole model. `impl Trait for Type:` is structural sugar over monomorphization: `check_impl` (`src/types/mod.rs`) resolves a trait bound to exactly one concrete type per call site, checked nominally but dispatched statically, exactly like an unbounded generic. There is no vtable anywhere in this compiler, no `dyn Trait`, and no `List<SomeTrait>` holding a runtime-mixed set of concrete types satisfying it.

**Decision: this is permanent, not a gap to close.** Real dynamic dispatch would need a fat-pointer/vtable value representation, a boxed-or-heap story for an unsized `dyn Trait` value, and a second codegen dispatch path bolted onto a compiler that is monomorphization-only end to end -- none of which fits the existing `frame`/arena/`GenRef` memory model (a boxed trait object isn't frame-allocatable, arena-scoped, or generation-checked the way every other reference type here is), and it would reopen exactly the kind of half-finished, partially-supported feature this project otherwise avoids. `impl Trait for ...` also only ever targets a `struct` (`check_impl`'s `self.structs.contains_key(...)` check, todo.md P1 #5's own open question) -- see `docs/language_reference.md`'s "Traits and Implementations" section for that restriction's current status.

**The actual answer for a heterogeneous collection** -- the motivating case a trait named `Damageable` implies: a mix of players, enemies, and destructibles in one list -- **is a tagged enum of variants, not a trait object**, and it costs nothing new, since data-carrying enum variants already exist:

```star
enum DamageableKind:
    PlayerK(player: Player)
    EnemyK(enemy: Enemy)

fn damage_all(mut things: List<DamageableKind>, amount: i32):
    for i in 0..things.len():
        match things[i]:
            DamageableKind::PlayerK(p) -> p.take_damage(amount)
            DamageableKind::EnemyK(e)  -> e.take_damage(amount)
```

The trait still documents and checks the shared method contract on each concrete type's own `impl`; the enum is what actually holds the mixed-type list, dispatched via `match` instead of a vtable call. See `docs/language_reference.md`'s "Heterogeneous Collections" section for the full pattern (verified compiling and running end to end).

**Future work, scoped but not planned.** If a real `dyn Trait` is ever justified, it would need at minimum: (1) a fat-pointer representation (`{ data: i8*, vtable: i8* }`) for a `dyn Trait`-typed value; (2) a decision on where that pointer's pointee lives, since arenas/`frame`/`GenRef` have no existing "boxed, unsized, dynamically-typed" storage class; (3) a second per-trait vtable-construction codegen path alongside the existing monomorphize-per-call-site path, including how it interacts with operator-overloading trait methods (`Add`/`Eq`/...) that today assume a single static type at the call site; and (4) an answer for how `par`/`swarm`'s per-system parallel iteration (which iterates one concrete component type per system) would type a system over a `dyn Trait` list at all. None of this is scheduled -- it's recorded here so a future revisit starts from this list instead of re-deriving it.


# Type System
Star's pitch is a single language spanning small indie titles, retro remakes/throwbacks and emulated retrocomputer systems, and AAA-quality games. Today's type system (`src/types/mod.rs`'s `Ty` enum) covers `i32`/`i8`/`u8`/`i16`/`u16`/`u32`/`i64`/`u64`, `f32`/`f64`, `char`, `str`, `bool`, `Vec2`/`Vec3`/`Vec4`, `Mat2`/`Mat3`/`Mat4`, `Quat`, `Color`/`Color32`, `Palette`/`PaletteIndex`, `List<T>`, `Map<K,V>`/`Set<T>`, `Tuple`/`Array`/`Ring<T,N>`/`Table<T>` (`(T, U, ...)`/`[T; N]`/`Ring<T, N>`/`Table<T>`), `GenRef<T>`/`Handle<T>`, `Wrapping<T>`/`Fixed<Bits,Frac>`, `Tick`/`Duration`/`Instant`, `Bytes`/`Symbol`, `BitField<N>`/`Flags<E>`, closures, and nominal structs/enums (including the builtin `Rect`/`Aabb2`/`Aabb3`/`Transform`/`Ray`/`Plane`/`Frustum`), plus `Option`/`Result` as true compiler-builtin generic enums with `?`-propagation sugar. That's every item this section originally set out to add: the "indie connective tissue" tier (§3's collection/compound types, §9's `Option`/`Result`), §7's resource handles, all of §2's numeric-width gap, §6's time types, all of §4's text/bytes gap, all of §8's bit-level types, and (as of this round) all of §5's math/geometry gap -- closing this section out entirely. Items marked **done** below are implemented and tested (`tests/frontend.rs`); this section is kept as a record of what was added and why, rather than a live plan.

1. Why one type system has to stretch three ways
Retro/emulation demands *exact-width, wrapping* arithmetic: an 8-bit CPU register or a PSG audio channel must overflow silently at 255 -> 0, which is the opposite of Star's current philosophy of trapping overflow as a bug. It also needs indexed/palette color and packed pixel formats, since that's how the hardware being emulated actually stores a frame.

AAA pulls the other way: `f64` for large-world coordinates without precision loss, quaternions to avoid gimbal lock, HDR linear color, and resource handles for GPU/audio assets that fail safely the way `GenRef` already does for despawned entities, plus string interning so per-frame tag/event comparisons across a huge entity count aren't `strcmp`.

Indie mostly needed the connective tissue both extremes assume already exists: `Option`/`Result` as real primitives (not a hand-rolled generic enum copied into every project), `Map`/`Set`, tuples, fixed-size arrays, a ring buffer, a struct-of-arrays table. Unglamorous, but until recently entirely absent — all seven are **done** now (see §3/§9's status below), closing out this tier entirely.

2. Numeric widths and modes -- **done**
`i8`/`u8`/`i16`/`u16`/`u32`/`i64`/`u64`/`f64` now exist alongside the original `i32`/`f32` as nine new `Ty` variants (`Ty::I8`/`U8`/`I16`/`U16`/`U32`/`I64`/`U64`/`F64`/`Char`), plus `char` (a Unicode scalar, distinct from a raw `str` byte -- lowered to a bare `i32` codepoint, see `Ty::Char`'s doc comment). `i64`/`f64` used to be accepted spellings that silently *aliased* `Ty::Int`/`Ty::Float` (the doc comment on `Checker::resolve_type`'s old code called this out as exactly this section's gap) -- they're genuinely distinct types now. Trap-on-overflow is the default for `+`/`-`/`*` on every one of these explicit-width integer types (via LLVM's `llvm.{s,u}{add,sub,mul}.with.overflow.iN` intrinsics, `Codegen::emit_checked_sized_int_arith`) and `/`/`%` trap on a zero divisor (plus, for a signed width, the lone `MIN / -1` overflow case) exactly like the pre-existing `i32` division guard, generalized to every width/signedness (`Codegen::emit_checked_sized_int_div`) -- **except** `Ty::Int` (`i32`) itself, which deliberately keeps its original silent two's-complement wraparound rather than retroactively changing behavior for a type every existing program already depends on; that gap (an intentional, documented scope cut, not an oversight -- see `Ty::I8`'s doc comment) is exactly what `Wrapping<T>` (below) closes. There is no implicit widening between any two distinct numeric types (the original `Int`/`Float` mixed-pair promotion -- `1 + 1.5 == 2.5` -- is the one preserved backward-compatible exception; every other pairing, e.g. `i8 + i64`, is a hard type-mismatch error). Moving a value between widths (or between a numeric type and `char`) requires a new explicit `expr as Type` cast expression (`Expr::Cast`/`TypedExpr::Cast`, a genuinely new, general-purpose grammar production -- `as` previously only appeared in `import "path.star" as alias`), lowered to the appropriate `trunc`/`sext`/`zext`/`sitofp`/`uitofp`/`fptosi`/`fptoui`/`fpext`/`fptrunc` per `Codegen::emit_cast`, mirroring Rust's own infallible truncating `as` (no runtime validation that a cast integer is a valid `char` codepoint, no `Result`-returning fallible-cast path). See `examples/numeric_widths.star`.
- `Wrapping<T>` -- **done**: silent-overflow arithmetic, for emulating an actual 8/16-bit register or audio-chip counter faithfully. `Ty::Wrapping(Box<Ty>)`, `T` restricted to any `int_shape()`-having type (including `Ty::Int` itself, closing the asymmetry noted above). Lowers to the *exact same* LLVM integer type as `T` -- zero overhead, no tag, mirroring how `Ty::Handle` reuses `Ty::GenRef`'s layout (see `crate::codegen::wrapping`). `+`/`-`/`*` are plain, untrapped opcodes (exactly `Ty::Int`'s own permanent exception, generalized to every width); `/`/`%` still trap on a zero divisor (matching Rust's own `Wrapping<T>` -- division-by-zero isn't "overflow"), but the one true overflow case (`MIN / -1`, `MIN % -1`) wraps instead of trapping, since LLVM's `sdiv`/`srem` are undefined behavior on that exact input regardless of the desired semantics. `Wrapping<T> as T` is a free bit-preserving relabel via the existing `as`-cast machinery. Deliberately *not* folded into `Ty::is_numeric()`/`int_shape()` (those also gate `sqrt`/`abs`/`pow`/FFI-scalar eligibility, none of which make sense for a "wrapping register") -- it gets its own dedicated dispatch branch in `Checker::infer_binop_ty`/`Codegen::emit_binop` instead, the same way `Vec2`/`Vec3`/`Vec4`/`Mat4`/`char`/`ptr` already do. See `examples/wrapping.star`.
- `Fixed<Bits, Frac>` -- **done**: deterministic fixed-point (e.g. `Fixed<32,16>`), for lockstep simulation and rollback netcode where float non-determinism across machines is a correctness bug, not a rounding nit. `Ty::Fixed(u32, u32)`, `Bits` restricted to `{8, 16, 32, 64}` and `Frac` to `0..Bits`. Lowers to a bare `i{Bits}` (Q format, signed) -- zero overhead, like `Ty::I8`. `+`/`-` reuse `emit_checked_sized_int_arith` as-is (no rescaling needed at that precision); `*`/`/` rescale by widening through `i128` *unconditionally* rather than doubling `Bits` itself (sign-extend, multiply-or-shift-then-divide, truncate back with a `sext(trunc(x)) == x` overflow check) -- LLVM natively supports `i128` `mul`/`sdiv` with no new intrinsic declarations needed, and a fixed 128-bit scratch width means a narrow `Fixed<8,4>` constructed from/computed with a wider source is never a correctness hazard, unlike a doubling scheme would be. `Fixed<Bits,Frac>(value)` accepts either an int-shaped value (an exact `shl` by `Frac`) or a `float`/`f64` (scaled by `2^Frac` then the pre-existing saturating `llvm.fptosi.sat` intrinsic `as` already declares for every width this needs -- the one well-defined float boundary this type allows, matching every other fixed-point library's `from_num`). `Fixed<Bits,Frac> <-> float/f64` is a new legal `as` pair (a true scaled conversion, not a bit reinterpret); no int<->`Fixed` cast and no `%` (both rejected by the checker -- construction is the only int entry point, and remainder isn't a meaningful fixed-point op). See `examples/fixed.star`; `crate::codegen::fixed`'s module doc comment has the full rescaling rationale.

3. Compound and collection types
```Python
[T; N]          # fixed-size inline array: tile grids, palettes, register files, vertex layouts -- done
(T, U, ...)     # tuple: lightweight multi-return without declaring a one-off struct -- done
Map<K, V>       # hash map: asset lookup tables, save data, tag indices -- done
Set<T>          # hash set -- done
Table<T>        # struct-of-arrays, complementing arena's array-of-structs for cache-batch AAA systems -- done
Ring<T, N>      # fixed-capacity ring buffer: input replay, frame-time history, netcode rollback buffers -- done
```
`Map<K,V>`/`Set<T>` (linear-scan lookup plus a generated structural-equality function per key/element type, not a hash table yet) landed first — see `examples/map_set.star`. `Tuple`/`Array` landed in the same round as each other: `(T, U, ...)` lowers to an anonymous LLVM literal struct (no `%name` declaration, unlike a nominal `struct`), positional elements read via a dedicated `.0`/`.1`/... `TupleIndex` node (not `Field`, which looks a name up in a *declared* struct); `[T; N]` lowers to a plain inline LLVM array, with the *only* literal form being the `[value; N]` repeat (a new `;` token/`TokenKind::Semi` — the only place the grammar uses one) since a distinct-elements form (`[e1, e2, e3]`) would collide with `List<T>`'s existing bracket literal and this checker has no expected-type propagation to disambiguate the two by context. Both are stored inline (no RC header, no heap allocation of their own) and are structurally hashable — usable as a `Map`/`Set` key/element type — exactly when composed entirely of hashable element types, mirroring a struct. See `examples/tuples_arrays.star`. `Ring<T,N>` landed next: also stored inline (an `{ [N x T], i64, i64 }` of data/head/len — no RC header, no heap allocation, no copy-on-write), like `Array` rather than `List`, but *mutable* through dedicated `push`/`pop` methods instead of being fully populated up front. `N` is written `Ring<T, N>` (angle brackets, alongside the element type argument, unlike `Array`'s `[T; N]`) since this compiler has no general const-generic parameter machinery to reuse — both the type position (`let h: Ring<i32, 3>`) and the `Ring<T, N>()` constructor needed a dedicated parser special case (`Parser::parse_type_inner`/`parse_ring_new`) rather than the ordinary comma-separated-`Type`-list turbofish, since `N` is a bare integer literal, not a `Type`. `push` grows while `len < N`, then evicts the oldest (front) element once full instead of growing (nowhere to grow to) or silently no-op'ing (`List`'s out-of-bounds-write convention) — a full ring always holds a sliding window of the most recent `N` pushes, matching the history-buffer/rollback use case; `pop` removes and returns the oldest element, FIFO-style. Not structurally hashable (no `Map`/`Set` key/element use, matching `List`). See `examples/ring.star`; `crate::codegen::ring`'s module doc comment has the full RC-safety invariant (every slot outside the live `[head, head+len)` window is always the element type's zero value) that lets the ordinary blanket retain/release walk stay correct with no length-aware special-casing. `Table<T>` landed last, closing out this section's "indie connective tissue" list: unlike every type above, `T` is a plain declared `struct` reflected over at codegen time (`Codegen::struct_field_types`) to lay out one parallel growable column per field instead of reusing a single-buffer storage shape wholesale — the payload is `{ i64 len, i64 cap, F0*, F1*, ... }`, one pointer per field of `T` in declaration order, all growing/shrinking in lockstep behind one shared `len`/`cap` pair. Lowered to the same reference-counted, copy-on-write `i8*` object pointer scheme as `List<T>`/`Map<K,V>`/`Set<T>` (unlike `Array`/`Ring`'s inline storage) — `Table<T>()`/method calls piggyback on the exact same generic-turbofish-plus-`StructLit` machinery those three already established (`Type::Generic("Table", [T])`, no dedicated AST node), since `Table<T>` (unlike `Ring<T,N>`) has only one type argument, a plain `Type`. `push`/`pop`/`len`/`table[i]`/`table[i] = v` mirror `List<T>`'s method surface and fails-safe OOB conventions exactly, just decomposing the whole element into (or reassembling it from) every column instead of touching one buffer slot. Place-projection through a table index (`table[i].field = v`, and any deeper chain rooted at one — `table[i].nested.x = v`, `table[i].tags.push(v)`, `table[i].cells[j] = v`) was closed out in a later round (todo.md P2 #10): `Codegen::emit_place`'s `Field` arm special-cases a `TableIndex` base (`Codegen::emit_table_field_place`), addressing the accessed field's real column slot directly rather than materializing the whole element into a disconnected temporary first — a single field's storage in this layout is a real, independently addressable column slot, it just needed its own dedicated place path instead of `emit_place`'s generic single-base-pointer `Field` GEP logic (which assumes one contiguous address to offset a field out of, which a table element's independent columns don't have). `Checker::writes_through_table_index` no longer rejects this shape; it's narrowed to its one remaining real gap, a *bare* table index passed somewhere a place is needed with no field projection yet applied (`reflect_set_i32(table[i], "field", v)` — mutating a whole struct by runtime field name still has no single contiguous address to target). See `examples/table.star`; `crate::codegen::table`'s module doc comment has the full column-layout rationale and the place-projection design.

4. Text and bytes -- **done**
`Bytes` -- **done**: an owned growable byte buffer distinct from `Str`, for asset formats, binary save data, and network payloads that aren't text. `Ty::Bytes` is a pure front-end generalization of machinery §3's `List<T>` already built and proved safe -- no new codegen representation, no new RC scheme: it reuses `List<u8>`'s exact reference-counted, copy-on-write `{ u8*, i64, i64 }` object-pointer layout and every one of its generated helpers (`push`/`pop`/`len`/`[i]`/`[i] = v`, growth-doubling, copy-on-write cloning) wholesale, by calling straight into `crate::codegen::list`'s existing functions with `elem_ty = Ty::U8` -- the same "reuse an existing generation-checked/RC'd layout under a second nominal wrapper" move `Ty::Handle` already made against `Ty::GenRef` (§7). The only new front-end work: a non-generic `Bytes()` constructor (rides the same capitalized-`Name(args)` `StructLit` grammar `Tick`/`Duration`/`Instant` already use, §6 -- no parser/AST changes), and threading `Ty::Bytes` through every exhaustive `Ty`-keyed match (`llvm_ty`/`mangle_ty`/`zero_value`/`type_align`/`type_size`/`contains_rc`/`emit_rc_walk`/`reflect_type_name`) with the identical arm `Ty::List` already has at each site. Deliberately kept nominally distinct from `Ty::List(Ty::U8)` (a function declared to take `Bytes` rejects a `List<u8>` argument and vice versa, same reasoning as `Handle<T>` vs. `GenRef<T>`) and *not* structurally hashable (no `Map`/`Set` key/element use, matching `List<T>`/`Ring<T,N>`). `bytes_from_str(s: str) -> Bytes`/`str_from_bytes(b: Bytes) -> str` (`crate::codegen::list`) convert to/from `Ty::Str` by copying bytes, since the two heap representations differ (`Bytes` isn't null-terminated and is never passed to `strlen`/`printf`'s `%s`). See `examples/bytes.star`.
`Symbol` -- **done**: an interned string with O(1) equality comparison, for entity tags and event names — at AAA entity counts, comparing tags with a byte-for-byte `str` compare every frame is a real cost. `Ty::Symbol` lowers to a bare `i64` id -- zero overhead beyond one process-wide intern table, the same "reuse the underlying integer type" move `Ty::Tick`/`Ty::Wrapping`/`Ty::Fixed` already make (§2/§6) -- deliberately excluded from `is_numeric()`/`int_shape()` for the same reason those three are, so it gets its own dedicated `==`/`!=`-only binop dispatch branch (`Checker::infer_binop_ty`/`Codegen::emit_binop`) rather than the numeric fast path; no ordering operators, since interning order is an implementation detail (first-seen order), not a meaningful sort. The intern table itself (`@sym.data`/`@sym.len`/`@sym.cap`, `crate::codegen::symbol`) is the one genuinely new piece of runtime machinery this round needed: a plain growable global array of owned `str` object pointers, doubled on grow via the *exact* `malloc`/`memcpy`/`free` recipe `ListMethod::Push` already uses (just against standalone globals instead of a heap payload struct's fields, since there's exactly one table for the whole process, itself never copied or reference-counted). `Symbol(s)` interns `s` via a linear `strcmp` scan against every already-interned string -- the same "no hashing yet" honesty `Map`/`Set` already have (§3) -- so *construction* cost grows with the table size, but every *comparison* between two already-constructed `Symbol`s is a single `icmp eq i64`, which is the O(1) guarantee this type actually promises; a match releases the freshly-evaluated argument (the table's independent copy is what stays alive), a miss transfers that same reference directly into the table with no retain/release (it lives for the remainder of the process). `symbol_name(sym) -> str` (`crate::codegen::symbol`) reverses the lookup, retaining a fresh, independently-owned copy of the table's permanent reference so the caller can release it on its own schedule; an out-of-range id (e.g. from a raw `as`-cast integer, never from `Symbol(..)`) yields `str`'s zero value, mirroring `List<T>`'s "safe null equivalent" OOB convention rather than crashing. `Symbol <-> i64` is a free bit-preserving relabel via `as`, for interop/debugging (printing the raw id). A legal `Map`/`Set` key (`Checker::check_hashable_ty`) -- comparison is just an integer compare -- which surfaced this round's one real bug: `crate::codegen::eq`'s generated per-key-type equality function has a `_ => "true".into()` fallback that's only safe when every hashable `Ty` has its own explicit arm; adding `Ty::Symbol` to `check_hashable_ty`'s true-arms without a matching arm in `emit_eq_body` silently made *every* `Symbol` compare equal to every other one inside a `Map`/`Set` (all keys collapsing into one slot) until the dedicated `icmp eq i64` arm was added there too -- now covered by a regression test (`runtime_symbol_as_set_key_dedups_end_to_end`). See `examples/symbol.star`.

5. Math and geometry -- **done**
Extends `Vec2`/`Vec3`/`Vec4`/`Mat4` in two different ways, split by how much of that existing machinery each new type can reuse wholesale:
```Python
Quat                     # quaternion rotation, no gimbal lock
Mat2, Mat3
Rect, Aabb2, Aabb3
Transform                # position + rotation + scale — the de facto universal ECS component
Ray, Plane, Frustum      # physics and culling
Color                    # f32 linear HDR, for AAA lighting pipelines
Color32                  # packed RGBA8, for indie-scale 2D/3D
Palette, PaletteIndex(u8)  # indexed color, for faithful retro console emulation
```
`Quat`/`Color` are new `Ty` variants that reuse `Ty::Vec4`'s exact `<4 x float>` layout wholesale -- the same "reuse an existing native-vector layout under a second nominal wrapper" move `Ty::Handle` already made against `Ty::GenRef` (§7). Both are folded into `is_vec()`/`vec_arity()` (arity 4), so field access (`.x`/`.y`/`.z`/`.w`, plus `.r`/`.g`/`.b`/`.a` as accepted aliases of the same four lanes -- `Codegen::swizzle_index`), componentwise `+`/`-`, scalar `*`/`/`, and the `dot`/`length`/`lerp` builtins all fall out for free, with zero new codegen. The one exception is `Quat * Quat`, special-cased ahead of the generic vector dispatch (`Checker::infer_binop_ty`/`Codegen::emit_binop`) to compute the true quaternion (Hamilton) product rather than a componentwise multiply -- the operation that actually composes two rotations; `quat_conjugate`/`quat_normalize`/`quat_rotate`/`quat_identity` (`crate::codegen::geometry`) round out the type-safe surface a bare `Vec4` has no business exposing (`quat_rotate` itself is implemented as `q * (v, 0) * conjugate(q)`, reusing the Hamilton-product codegen twice rather than re-deriving the equivalent cross-product formula). `Mat2`/`Mat3` are new `Ty` variants generalizing what used to be `Mat4`-only matrix codegen (`emit_mat4_addsub`/`emit_mat4_mul`/`emit_mat4_vec4_mul`) to a `mat_dim()`-driven dimension parameter (2/3/4) -- `Mat2` lowers to `[2 x <2 x float>]`, `Mat3` to `[3 x <3 x float>]`, exactly `Mat4`'s own "row of native vectors" shape at a smaller fixed size, constructed as `Mat2(row0, row1)`/`Mat3(row0, row1, row2)` mirroring `Mat4(row0, row1, row2, row3)`.

`Color32` is a new `Ty` lowering to a bare `i32` (packed `r | g<<8 | b<<16 | a<<24`) -- zero overhead beyond the pack/unpack arithmetic itself, the same "reuse a bare integer" move `Ty::Tick`/`Ty::Symbol` already make; deliberately excluded from `is_numeric()`/`int_shape()` for the same reason those two are, with its own `==`/`!=`-only binop dispatch, a free bit-preserving `as`-cast to/from `i32`/`u32`, and a legal `Map`/`Set` key (`Checker::check_hashable_ty`, with its own explicit `crate::codegen::eq` arm -- the "every hashable `Ty` needs its own arm or silently collapses every key into one slot" bug class `Ty::Symbol` once shipped with, §4). `color_to_color32`/`color32_to_color`/`color32_r`/`color32_g`/`color32_b`/`color32_a` (`crate::codegen::geometry`) convert to/from `Color` and unpack individual channels; an HDR `Color` channel outside `[0, 1]` is clamped (via the same `llvm.maxnum.f32`/`llvm.minnum.f32` intrinsics `Codegen::emit_clamp` already declares unconditionally) before the saturating `llvm.fptoui.sat.i32.f32` intrinsic converts it, rather than an unguarded `fptoui` that would be undefined behavior on an out-of-range/NaN input. `PaletteIndex` is a new `Ty` lowering to a bare `u8` (the same "reuse the underlying integer type" move as `Ty::Wrapping`/`Ty::BitField`), constructed from any `int_shape()`-having value narrowed to `u8` and free-`as`-castable to/from `u8`; `Palette` is a new `Ty` reusing `List<Color32>`'s exact reference-counted, copy-on-write layout and method surface wholesale, the same move `Ty::Bytes` already made against `List<u8>` (§4) -- `Palette()` starts empty, `pal[i]` requires a plain `i32` index like any `List<T>` (an explicit `as i32` bridges a `PaletteIndex`), and `push`/`pop`/`len` are routed straight into `crate::codegen::list` with `elem_ty = Ty::Color32`.

`Rect`/`Aabb2`/`Aabb3`/`Transform`/`Ray`/`Plane`/`Frustum` need **no new `Ty` variant and no new codegen at all**: each is a plain, non-generic `struct` composed entirely of types the checker/codegen already fully understand (`f32`, `Vec2`, `Vec3`, `Quat`, a fixed-size `[Plane; 6]` array), synthesized in Rust as an ordinary `StructDef` AST value and pre-registered directly into `Checker::structs` before any user code is scanned (`crate::types::builtin_structs`) -- the same "seed the name up front so a user redeclaration hits the ordinary duplicate-name diagnostic instead of silently shadowing the builtin" move `Option`/`Result` already make for `type_names_seen` (§9), just against `self.structs` instead of `self.generic_enums`. Unlike `Option`/`Result` (generic templates with no concrete layout of their own until monomorphized, so the template itself is never emitted), each of these 7 is immediately checked into a concrete `TypedItem::Struct` -- *right after* pre-registration, before pass 0 processes any user declaration, since deferring that to the end of `Checker::check` (alongside the monomorphized-item list, `self.mono_items`) would type-check a field default like `Aabb2.min`'s `Vec2(0.0, 0.0)` *after* a user module's own conflicting `struct Vec2: ...` (a legitimate, already-tested shadowing feature) had already overwritten the real builtin in `self.structs`, corrupting arity checking on a default the user's source never wrote. The 7 resulting `TypedItem::Struct`s are appended to the typed module *after* every ordinary item, so they never shift a real user declaration's position in the final typed list (several of this crate's own existing tests index `typed.items[N]` assuming index 0 is the file's own first declaration). Because every field is a plain value type, construction (named or positional, with defaults), field access, layout, and RC-safety (none of these fields carry RC content) all fall out of the ordinary user-struct pipeline automatically -- only their handful of characteristic operations need a dedicated free function, in a new `crate::codegen::geometry` module: `rect_contains`/`rect_intersects`, `aabb2_contains`/`aabb2_intersects`, `aabb3_contains`/`aabb3_intersects`, `ray_at`, `plane_distance_to_point`, `frustum_contains_point` (checks a point against all six of a `Frustum`'s planes), and `transform_apply_point` (position + `quat_rotate(rotation, point * scale)`). See `examples/quat.star`/`examples/matrices.star`/`examples/color.star`/`examples/geometry.star`/`examples/palette.star`.

6. Time -- **done**
`Tick` (integer simulation-step counter, matching `sequence`'s existing tick model), `Duration` (wall-clock, e.g. `i64` nanoseconds), `Instant` (monotonic timestamp). Keeping these distinct from a bare `f32` delta-time avoids the drift and non-determinism bugs that break replay recording and rollback netcode. All three are nominal types (`Ty::Tick`/`Ty::Duration`/`Ty::Instant`) lowering to a bare `i64` -- zero overhead, exactly `Ty::Wrapping`/`Ty::Fixed`'s "reuse the underlying integer type" approach, and (like those two) deliberately excluded from `is_numeric()`/`int_shape()` so a `Tick` can't be silently mixed into ordinary integer arithmetic. Construction (`Tick(value)`/`Duration(value)`/`Instant(value)`) accepts any `int_shape()`-having value, widened/narrowed to `i64` (`Codegen::emit_time_new`, mirroring `Ty::Fixed`'s own int-shaped construction path minus its `Frac` rescale). Unlike `Wrapping`/`Fixed`'s uniform "operands must match exactly" rule, the three types' legal operator set is deliberately *asymmetric* -- mirroring Rust's own `std::time::{Instant,Duration}` API rather than treating all three as interchangeable tagged integers: `Tick + i64 -> Tick`/`Tick - i64 -> Tick` (advance/rewind by a step count) and `Tick - Tick -> i64` (a tick delta, since summing two absolute tick counts has no sensible meaning, unlike subtracting them); `Duration + Duration -> Duration`/`Duration - Duration -> Duration`; `Instant - Instant -> Duration` (elapsed time) and `Instant +/- Duration -> Instant`; plus the six comparison operators between two values of the same type. Every other pairing (mixing the three with each other outside that table, or with a bare `i32`) is a hard type error, same "no implicit anything" rule every other explicit-width type in this section follows -- see `Checker::infer_time_binop_ty`. `Tick`/`Duration`/`Instant` <-> `i64` is a free bit-preserving relabel via the existing `as`-cast machinery, same as `Wrapping<T> <-> T`. See `examples/time_types.star`.

7. Resource handles -- **done**
Generalize the `GenRef<T>` pattern — already generation-checked, already proven safe for arena entities — to engine resources: `Handle<Texture>`, `Handle<Mesh>`, `Handle<Shader>`, `Handle<Sound>`. A freed texture handle used after unload fails the same safe generation-check path `GenRef` already gives despawned entities, instead of segfaulting the renderer. This is a reuse of existing machinery, not a new safety mechanism: `Ty::Handle(Box<Ty>)` lowers to the exact same `%GenRef = type { i32, i32 }` layout and the exact same arena-backed construction/dereference codegen (`Codegen::emit_genref_create`/`emit_genref_index`/`emit_genref_index_place`) as `Ty::GenRef` -- same `arena Name: T` backing declaration, same `spawn`/`despawn` lifecycle, same stale/OOB "safe zero value" fallback. The only new work is at the front end: `Handle<T>(value)` parses through the identical special-cased grammar `GenRef<T>(value)` already needed (`Expr::GenRefCreate` gained an `is_handle` flag rather than a second AST node, since every downstream pass that doesn't care about the distinction already matched on `{ .. }`), and `Ty::Handle` is a genuinely distinct nominal type from `Ty::GenRef` -- a function declared to take `Handle<Texture>` rejects a `GenRef<Texture>` argument and vice versa, even though they're byte-identical at runtime, so a resource handle can never be silently swapped for an unrelated entity reference. See `examples/handle_resource.star`.

8. Bit-level types -- **done**
`Flags<E: Enum>` and `BitField<N>` close out this section entirely -- see `Ty::Flags`/`Ty::BitField`'s doc comments in `src/types/mod.rs`. Neither invents new operator grammar (`&`/`|`/`^`/`~`/`<<`/`>>` don't exist anywhere in this language): both expose a dedicated free-function surface instead, mirroring the `symbol_name`/`bytes_from_str` idiom §4's `Symbol`/`Bytes` already established, rather than the arithmetic-operator dispatch `Wrapping<T>`/`Fixed<Bits,Frac>` use -- neither type has anything resembling `+`/`-`/`*` to overload in the first place. `BitField<N>` (`N` restricted to `{8, 16, 32, 64}`, the same widths `Fixed<Bits,Frac>`'s `Bits` already restricts to) lowers to a bare `i{N}` -- zero overhead, exactly `Ty::Fixed`'s own "reuse the underlying integer type" move -- and is constructed from any int-shaped value widened/narrowed to `i{N}` (`BitField<N>(value)`, parsed via a dedicated `Expr::BitFieldNew` node mirroring `Fixed<Bits,Frac>`'s own single-turbofish-shape special case, since `N` is a bare integer literal, not a `Type`). Its free-function surface -- `bit_get(x, i) -> bool`/`bit_set(x, i)`/`bit_clear(x, i)`/`bit_toggle(x, i)`/`bit_and(a, b)`/`bit_or(a, b)`/`bit_xor(a, b)`/`bit_not(x)` -- isn't restricted to `BitField<N>` alone: `Ty::bit_shape()`/`Ty::bitwise_combine_shape()` also accept any `int_shape()`-having type and `Wrapping<T>`, since the retro-register-emulation use case this section is motivated by in practice needs bit tricks on a plain `u8` register just as often as on a dedicated `BitField<8>`. A bit index is masked mod its register's width before shifting (`idx & (width - 1)`, `width` always a power of two) rather than passed straight to LLVM's `shl` -- an out-of-range shift amount is a poison value under LLVM's semantics (unlike x86 hardware `shl`, which masks the count itself in the CPU), so an unguarded out-of-range `bit_get(x, 99)` on an 8-bit `x` was undefined behavior, not just a wrong-but-safe answer, until this masking was added (caught by `runtime_bitfield_out_of_range_index_wraps_rather_than_traps_end_to_end`).

`Flags<E>` requires `E` to resolve to a fieldless enum (the same restriction `Checker::check_hashable_ty` already applies to a fieldless-enum `Map`/`Set` key) with 64 or fewer variants -- one bit per variant, in declaration order, always packed into a bare `i64` regardless of `E`'s actual variant count (the same "one fixed width regardless of the logical range" simplicity `Ty::Symbol`'s intern id already accepts). Constructed via `Flags<E>(a, b, ...)`, a variadic list of zero or more `E`-typed arguments OR'd together -- parsed as an ordinary `Expr::StructLit` naming the builtin `Flags` type (the same turbofish-plus-call grammar `List<T>`/`Table<T>` already use, needing zero new parser/AST work, unlike `BitField<N>`) rather than a dedicated AST node, with `Checker::infer_flags_new` synthesizing a new HIR-only `TypedExpr::FlagsNew` node once every argument's checked to be `E`-typed. Each argument's bit is computed at codegen time as `1i64 << variant_tag`, reading the already-evaluated fieldless enum value's own bare `i32` runtime discriminant directly (`Codegen::emit_flags_variant_bit`) -- so a *runtime* enum-typed expression works as a construction argument too, not just a literal `EnumName::Variant`, with no compile-time variant-name lookup needed at all (unlike `Codegen::enum_variant_index`, which `EnumVariant` literal codegen uses instead, since that node carries a variant name rather than an already-evaluated expression). `flags_has(f, e) -> bool`/`flags_with(f, e) -> Flags<E>`/`flags_without(f, e) -> Flags<E>`/`flags_is_empty(f) -> bool` round out the type-safe, enum-variant-typed surface; `bit_and`/`bit_or`/`bit_xor` (but deliberately not `bit_not`/`bit_get`/`bit_set`/`bit_clear`/`bit_toggle`) are shared with `BitField<N>`'s own free functions for union/intersect/symmetric-difference, safe to share since both operands only ever have bits set for real declared variants so the result never gains an undefined bit -- raw bit-indexing a flag set is excluded on purpose, since it would defeat the type safety `flags_has`/`flags_with` exist to provide. Both types support `==`/`!=` (a bare bit-pattern/mask comparison, the same `==`-only dispatch branch `Ty::Symbol` uses -- no ordering, a packed register/flag set has no meaningful "less than") and are legal `Map`/`Set` keys (`Checker::check_hashable_ty`, with their own explicit `crate::codegen::eq` arms -- the exact "every hashable `Ty` needs its own arm or silently collapses every key into one slot" bug class `Ty::Symbol` once shipped with, see this section's own regression tests for the defensive coverage); `BitField<N> <-> i{N}`/`u{N}` and `Flags<E> <-> i64` are both free bit-preserving relabels via the existing `as`-cast machinery, mirroring `Ty::Wrapping<T> <-> T`/`Ty::Symbol <-> i64`. See `examples/bitfield.star`/`examples/flags.star`, `crate::codegen::bitfield`/`crate::codegen::flags`.

9. `Option`/`Result` as compiler primitives -- done
Promoted from a user-space generic enum (as the docs example used to show) to true builtins: `Checker::check` synthesizes and registers the `Option<T>`/`Result<T,E>` generic-enum templates as if they'd been parsed from source (`src/types/mod.rs`'s `builtin_generic_enums`) before any user code is scanned, and `expr?` desugars to a `match` over their `Some`/`None`/`Ok`/`Err` variants with early `return` (`Expr::Try`) — there is no dedicated codegen path for `?` at all, just the ordinary generated `match`/enum machinery.

10. Sequencing
The lowest-effort, highest-value slice — `Option`/`Result` as builtins + `Map`/`Set` + tuples + fixed-size arrays, all indie-tier gaps that unblock ordinary programs immediately and required no new codegen primitives beyond what generics/`List<T>`/nominal structs already established — is now **done**. `Ring<T,N>` (fixed-capacity ring buffer) is now **done** too, a straightforward extension of patterns this compiler already has (`Array`'s inline no-RC-header storage, `List`'s `push`/`pop` method shape). `Table<T>` (struct-of-arrays) is now **done** as well, closing out this section's indie-tier list entirely: a bigger lift than `Ring<T,N>` was, since `T` is generically a *struct* type whose fields needed to be reflected over at codegen time (`Codegen::struct_field_types`) to lay out one parallel growable column per field, rather than reusing an existing single-buffer storage shape wholesale — but it reuses `List<T>`'s reference-counted, copy-on-write `i8*` object-pointer scheme wholesale (unlike `Ring<T,N>`'s inline storage), and — unlike `Ring<T,N>`, which needed a dedicated parser/AST node since its `N` is a bare integer literal — `Table<T>` has only one type argument, a plain `Type`, so `Table<T>()`/method calls piggyback on the exact same generic-turbofish-plus-`StructLit` machinery `List<T>`/`Map<K,V>`/`Set<T>` already established, with zero parser or AST changes. Resource handles (`Handle<T>`, §7) are now **done** too: the smallest of the remaining items, since it's a pure front-end generalization of machinery §1's `GenRef<T>`/arena work already built and proved safe -- no new codegen, no new runtime representation, just a second nominal wrapper type sharing the same generation-check path. §2's numeric-width/`char`/cast work turned out to be the largest single lift this section has seen -- it touched the lexer (a new `'c'` char-literal token), the parser (a new `as`-cast grammar production, the first new binary-operator-precedence-tier addition since the original grammar), the checker (nine new `Ty` variants, a generalized "any numeric type" predicate replacing the old `Int`/`Float`-only one, and a new cast-legality check), and every arithmetic codegen path (`Codegen::emit_scalar_binop` now dispatches to a width/signedness-generic sized-integer path with real overflow-trap intrinsics, not just the original `i32`-only opcodes) -- and is now **done**, per §2's own entry above. `Wrapping<T>`/`Fixed<Bits,Frac>` (the two explicit opt-in modes trap-on-overflow needs *not* to be the only option) are now **done** too, closing out §2 entirely: `Wrapping<T>` was a comparatively small lift, reusing `Ty::Int`'s own pre-existing untrapped-arithmetic path (generalized to every width) plus the existing `as`-cast machinery for its bit-preserving unwrap, with only its `/`/`%` guard (wrap `MIN / -1` instead of trapping) genuinely new; `Fixed<Bits,Frac>` was the bigger of the two, needing a new two-integer-literal type-position parser special case (mirroring `Ring<T,N>`'s own), a new `<Bits,Frac>(value)` construction grammar (mirroring `GenRef<T>`/`Handle<T>`'s `<T>(value)` shape closely enough to extend that same `parse_postfix` dispatch), and a new `i128`-widening rescale path for `*`/`/` that reuses `as`'s pre-declared saturating `fptosi.sat` intrinsics for its float boundary rather than declaring anything new. Neither type was folded into `Ty::is_numeric()`/`int_shape()` -- both get their own dedicated dispatch branch in the checker's binop-type-inference and the codegen's binop-emission entry points instead, alongside the pre-existing `Vec2`/`Vec3`/`Vec4`/`Mat4`/`char`/`ptr` branches there. §6's time types (`Tick`/`Duration`/`Instant`) are now **done** too: a small lift relative to `Wrapping`/`Fixed`, since all three are non-generic nominal types (no type-position parser work needed at all -- a plain capitalized identifier already resolves to `Type::Named`) that reuse `Vec2`/`Vec3`'s existing `Name(args)` construction grammar as-is. The one genuinely new piece of checker machinery is `Checker::infer_time_binop_ty`: unlike `Wrapping`/`Fixed`'s uniform "operands must match exactly" dispatch, these three need an *asymmetric* legal-pairing table (`Tick + i64 -> Tick`, `Tick - Tick -> i64`, `Instant - Instant -> Duration`, `Instant +/- Duration -> Instant`, ...) mirroring Rust's own `std::time::{Instant,Duration}` API, so it's factored into its own dedicated function rather than squeezed into the existing uniform-dispatch shape. Codegen was the smallest part: all three lower to a bare `i64` (`crate::codegen::time`), so construction is just an int-shaped widen/narrow and every operator that reaches codegen is exactly the same checked-`i64`-add/sub-plus-signed-comparison regardless of which of the three (or plain `i64`) the checker typed the result as. §4's text/bytes types are now **done** too, closing out this section's "indie connective tissue" *and* its text/bytes gap entirely: `Bytes` was the smaller of the two, a pure front-end generalization exactly like `Handle<T>` (§7) was -- reusing `List<u8>`'s existing reference-counted, copy-on-write layout and every generated method wholesale, with no new codegen representation and no new RC scheme, just a second nominal wrapper threaded through each exhaustive `Ty`-keyed match. `Symbol` needed one genuinely new piece of runtime machinery -- a process-wide intern table (`crate::codegen::symbol`), a plain growable global array doubled via the same `malloc`/`memcpy`/`free` recipe `List<T>::push` already established, just against standalone globals instead of a heap payload struct's fields -- but was otherwise a small lift: a bare `i64` id (zero overhead, like `Tick`/`Wrapping`/`Fixed`), its own dedicated `==`-only binop branch, and a free `as`-cast relabel to/from `i64`. This round also surfaced (and fixed) a real latent bug: `crate::codegen::eq`'s generated per-key-type equality function relies on every legal `Map`/`Set` key type having its own explicit arm, silently falling back to "always equal" otherwise -- adding `Ty::Symbol` to `Checker::check_hashable_ty`'s legal-key list without a matching `emit_eq_body` arm would have shipped a `Symbol` that silently collapsed every distinct key into one `Map`/`Set` slot, caught before release by `runtime_symbol_as_set_key_dedups_end_to_end`. §8's bit-level types (`BitField<N>`/`Flags<E>`) are now **done** too, closing out the whole section: both were a comparatively contained lift, deliberately built as a free-function surface (`bit_get`/`bit_set`/`bit_and`/..., `flags_has`/`flags_with`/...) rather than new bitwise-operator grammar, since `&`/`|`/`^`/`~` don't exist anywhere in this language yet and inventing them would have been a far bigger, unrelated lift (the numeric-width round's own `as`-cast addition remains "the first new binary-operator-precedence-tier addition since the original grammar" for a reason). `BitField<N>` reused `Ty::Fixed`'s exact "bare `i{N}`, dedicated single-turbofish parser special case" shape; `Flags<E>` needed no new parser/AST work at all (`Flags<E>(a, b, ...)` rides `List<T>`/`Table<T>`'s existing turbofish-plus-call grammar), just a new HIR-only `TypedExpr::FlagsNew` synthesized by the checker and a codegen trick worth calling out: each construction argument's bit is `1i64 << variant_tag`, read directly off the already-evaluated fieldless enum value's own runtime discriminant, so a *runtime* enum-typed expression works as a construction argument, not just a literal `EnumName::Variant` (no compile-time variant-name lookup needed the way `EnumVariant` literal codegen's `Codegen::enum_variant_index` requires). This round found two more real bugs, one in each direction of "how much stack a growing compiler needs": an LLVM correctness bug (`bit_get`/`bit_set`/... shifted by a raw, unmasked bit index -- an out-of-range shift amount is a poison value under LLVM's `shl` semantics, not a wrapped one, so an out-of-bounds index was undefined behavior until the shift amount was masked mod the register's width first) caught by `runtime_bitfield_out_of_range_index_wraps_rather_than_traps_end_to_end`; and a pre-existing stack-safety regression this round's own match-arm growth pushed over the edge -- `rejects_deeply_nested_parens_does_not_overflow_stack`/`runtime_moderately_long_binary_chain_end_to_end` (150 chained `+` operators, well under `Parser::MAX_BINARY_CHAIN`'s 200-operator promise) both overflowed the real stack, reproducible even through a standalone `star build` on the OS's own default main-thread stack, not just `cargo test`'s. Rather than keep shrinking `MAX_EXPR_DEPTH`/`MAX_BINARY_CHAIN` (a real, user-visible regression in how much legitimately-nested/long input compiles, and a fix that would only need re-doing again next round) every time a future feature's match arms grow `parse_primary`/`Checker::infer_expr`/`Codegen::emit_expr`'s already-large stack frames a little further in an unoptimized build, `main`'s actual work now runs on a purpose-spawned 32MiB-stack thread (`src/main.rs`'s `MAIN_STACK_SIZE`, the same fix real compilers with deep AST recursion, e.g. `rustc`, already use) and `cargo test`'s own per-test threads get the same headroom via `RUST_MIN_STACK` in `.cargo/config.toml`, so this class of fix scales with future growth instead of fighting it test-by-test. §5's math/geometry gap is now **done** too, closing out this section (and this Type System write-up) entirely -- the largest item count of any single round, but split cleanly by how much existing machinery each new type could reuse: `Quat`/`Color` cost almost nothing, since folding them into `is_vec()`/`vec_arity()` gives them `Vec4`'s entire field-access/arithmetic/builtin surface for free, with only `Quat * Quat`'s Hamilton product (composing two rotations, not a componentwise multiply) needing real new codegen; `Mat2`/`Mat3` were a pure generalization exercise, turning three `Mat4`-only functions into one dimension-generic set (parameterized by `mat_dim()`) that `Mat4` itself now also routes through; `Color32`/`PaletteIndex`/`Palette` each reused a "bare scalar" or "wraps `List<T>`" precedent already established by `Tick`/`Symbol`/`Bytes` in §4/§6. The real surprise was `Rect`/`Aabb2`/`Aabb3`/`Transform`/`Ray`/`Plane`/`Frustum`: composed entirely of types the checker/codegen already understood, they needed no new `Ty` variant and no new codegen at all, just a `struct` synthesized in Rust and pre-registered into `Checker::structs` the same way `Option`/`Result` are pre-registered into `generic_enums` (§9) -- but unlike those two generic templates (never themselves emitted), these 7 are concrete and *do* need a real `TypedItem::Struct` for codegen to see, which surfaced a genuine ordering hazard this round found and fixed: checking a builtin's field default (e.g. `Aabb2.min`'s `Vec2(0.0, 0.0)`) has to happen immediately after pre-registration, before any user item is processed, or a user module exercising the already-tested "a struct named `Vec2` shadows the builtin scalar" feature would silently corrupt that default's arity checking once its own conflicting `Vec2` overwrote the real one in `self.structs`. The 7 resulting typed items are appended after every user item precisely so they never perturb the positional-index assumptions several of this crate's own pre-existing tests make about `typed.items[0]`/`[1]`.
